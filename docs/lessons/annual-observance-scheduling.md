# 年度紀念日產線：排程稿不會自己上線，而且坊間的紀念日對照表會騙你

> 摘要
> - **`status: scheduled` 的文章不會自己上線**：`isPublic()` 比對的是 **build 當下的時間**，不是真實時鐘。沒有人在 `publishDate` 之後觸發一次 build，文章就一直是 noindex 預覽頁。`deploy.yml` 的 6 小時 cron（台北 02/08/14/20）對不上任何非整點的排程時間。
> - **精確到分的上線時間，必須另排一支準點觸發 deploy 的 cron**，且「時間戳準」與「可見時刻準」二選一，不可能同時滿足（build 要 3-5 分鐘）。
> - **「提前 N 天寫」要掃區間不能掃單日**，否則失敗就永遠補不回來；配合冪等帳本，重試是免費附贈的。
> - **網路上流傳的健康紀念日對照表有過期與錯誤**，照抄會每年錯一次。三筆已證實：世界癲癇日、世界高血壓日、世界肥胖日。權威來源是衛福部核定清單與各發起組織官網。
> - 浮動日期（「3 月第二個星期四」）**必須寫成規則由程式解**，不能寫死某一年的日期。

相關：[`auto-publish-pipeline-traps.md`](./auto-publish-pipeline-traps.md)（publishDate 用系統時間蓋、worktree 要先 build）、[`duplicate-topic-gate.md`](./duplicate-topic-gate.md)（年復一年同題的競食風險）。

---

## 一、排程稿不會自己上線

### 問題

站長要求「每年固定的紀念日都在台北 06:17 看到一篇文章」。直覺作法是提前寫好、設 `status: scheduled` 與 `publishDate: <當日>T06:17:00+08:00`，然後等它自己上線。

它不會。

### 原因

`src/utils/content.ts` 的 `isPublic()`：

```ts
return a.data.publishDate.getTime() <= Date.now();
```

`Date.now()` 是 **build 執行當下**的時間。這是靜態網站，不是有 runtime 的伺服器——沒有任何東西會在 06:17 那一刻重新判斷一次。文章要從「排程草稿預覽頁」變成正式文章，唯一途徑是**在 `publishDate` 之後跑一次 build**。

而 `deploy.yml` 的觸發條件只有三個：push 到 `main`、`cron: '0 */6 * * *'`（台北 02、08、14、20）、手動 `workflow_dispatch`。**六小時一次的整點 cron 對不上 06:17**，排程稿最快要等到台北 08:00 才會上線，遲了 1 小時 43 分。

### 解法

寫作與上線拆成**兩支 cron**：

| | 時間 | 做什麼 | 喚 Claude？ |
|---|---|---|---|
| `health-days.sh` | UTC 03:00（台北 11:00） | T-2 天抓當年度素材寫稿，推 main，此時只是排程稿 | ✅（且有純資料前置 gate） |
| `health-days-publish.sh` | UTC 22:17（台北 06:17） | 查有沒有排今天 06:17 的稿，有才 `gh workflow run deploy.yml` | ❌ 純 shell |

上線那支刻意做成純 shell：不碰 git 工作區、不走 worktree、不喚 Claude，只有一次 `git grep origin/main` 加一次 `gh workflow run`。每天跑成本近乎零。

### 怎麼避免重犯

- 任何「要在某個精確時刻上線」的需求，都要問一句：**那個時刻有沒有東西會觸發 build？** 靜態站沒有 runtime，排程只是 build 時的過濾條件。
- 別為了對齊而把 `deploy.yml` 的 6 小時 cron 改密。那會讓全站每次都重跑完整 build（含 Pagefind、字型子集、圖片壓縮），成本與 CI 排隊都不划算，而且仍然只能對齊到你設定的那幾個整點。

## 二、「提前 N 天寫」如果寫成「剛好第 N 天」，就沒有重試能力

### 問題

提前兩天寫稿的直覺實作是「看 T+2 那一天有沒有紀念日」：

```js
const targets = healthDaysAhead(taipeiToday(), 2);   // ← 剛好第 2 天
```

這在順利時完全正確，**失敗時卻永遠補不回來**。以 8/31 為例：8/29 跑（T+2）命中，若 Claude 撞用量上限或文章被 gate 剔除而沒寫成，8/30 跑的是 9/2——8/31 那篇再也不會出現在任何一次執行的視野裡，當天就是開天窗。

這個缺陷不會在測試裡浮現，因為每一次單獨執行看起來都是對的。

### 解法

掃**區間** T+1 … T+N，而不是單一天：

```js
export function healthDaysWithin(fromDate, leadDays) {
  const out = [];
  for (let i = 1; i <= leadDays; i++) out.push(...healthDaysAhead(fromDate, i));
  return out;
}
```

配合「該年度已寫過就跳過」的帳本（`ledgerKey = <slug>@<年份>`），重試是免費附贈的：8/30 那次會再看到 8/31，帳本裡沒有紀錄就重寫一次；寫成了就自動跳過。不需要額外的重試佇列或狀態機。

刻意**不含 T+0**：上線 cron 在台北 06:17 跑、寫稿 cron 在 11:00，當天才寫已經來不及。

區間可能跨年（12/31 往後 2 天落在隔年），所以年份要**逐筆從各自的日期取**，不能拿 `targets[0]` 的年份套用到全部。

### 怎麼避免重犯

任何「提前 N 單位處理」的排程，都要問：**這一批處理失敗了，下一次執行還看得到它嗎？** 若答案是否，就把「單點」改成「區間」，並用冪等的已完成帳本收斂。這比加重試邏輯簡單，也不會有重試次數耗盡的狀態要維護。

## 三、「06:17 看到」與「時間戳寫 06:17」不可能同時成立

從 `workflow_dispatch` 觸發到文章線上可讀，要跑完 build（約 126 秒）＋ Pages 部署＋ CDN 傳播，實測約 3-5 分鐘。所以：

| 作法 | 時間戳 | 實際可見 |
|---|---|---|
| publishDate 06:17，06:17 觸發 | 6:17 ✅ | 約 6:21 |
| publishDate 06:00，06:12 觸發 | 6:00 ❌ | 6:16 ✅ |

想「06:12 觸發、publishDate 06:17」是行不通的：build 在 06:15 執行時 `Date.now()` 還沒到 06:17，文章仍會被 `isPublic()` 濾掉。

站長 2026-07-28 選了前者（時間戳準）。**這是取捨不是 bug，別再「修正」它。**

## 四、坊間的紀念日對照表會騙你

### 問題

企劃清單直接抄自網路流傳的「月旦醫事法網·世界醫療相關紀念日」對照表。這份表在中文圈被大量轉載，看起來很權威（有英文名、有發起組織），但它多列自承「Google 找的到相關文章說明有這個紀念日，但設立由來及組織不明」，而且**內容停留在製表當時**。

實際查證後有三筆是錯的：

| 紀念日 | 該表 | 實際 | 說明 |
|---|---|---|---|
| 世界癲癇日 | 2 月 14 日 | **2 月第二個星期一** | IBE＋ILAE 2015 年共同發起時就是浮動日；2/14 是情人節，疑似張冠李戴 |
| 世界高血壓日 | 5 月第二個星期六 | **5 月 17 日** | 2005 年首屆確實是浮動日，但 WHL **2006 年起改固定 5/17**，該表停在首屆 |
| 世界肥胖日 | 10 月 11 日 | **3 月 4 日** | 世界肥胖聯盟 **2020 年起變更**；10/11 是 2015-2019 的舊制 |

一個紀念日產線每年跑一次，日期錯了就是**每年錯一次、而且沒人會發現**（讀者不會來信說「你們的世界癲癇日寫錯天了」）。

### 原因

紀念日的日期會變。發起組織會為了「與其他活動錯開」「擴大影響力」而改期（世界肥胖日就是這個理由），也會從浮動日改成固定日（世界高血壓日）。二手對照表沒有維護機制，改期不會回頭更新。

### 解法

建表時逐條對**一手來源**核對，並把來源與已知錯誤寫進資料檔檔頭（`scripts/lib/health-days.mjs`）：

- **台灣醫事人員節日** → 衛生福利部依《紀念日及節日實施條例》公告的「所定紀念日及節日由來說明」（21 項核定，含由來與核定文號脈絡）。這份文件同時解決了「台灣到底有哪些醫事人員節」的問題——實際有 21 個，遠多於一般清單收的三五個。
- **國際紀念日** → 各發起組織官網（WHO、UICC、IDF、WHL、IBE＋ILAE、IOF…）。

單元測試釘住已知錯誤，讓任何人「好心改回去」時會被擋下：

```js
it('已知的三筆坊間錯誤日期沒有被抄進來', () => {
  expect(healthDaysOn('2027-02-14')).toEqual([]);              // 癲癇日不是 2/14
  expect(healthDaysOn('2027-10-11')).toEqual([]);              // 肥胖日不是 10/11
  expect(healthDaysOn('2027-03-04').map(h => h.slug)).toEqual(['world-obesity-day']);
});
```

### 怎麼避免重犯

- 建任何「年復一年自動執行」的資料表，**逐條查一手來源**，並在檔頭寫明查證日期與已知的錯誤二手來源。錯誤的成本會乘以年數。
- 用語一併校正。這批的中國用語混入特別多：阿爾茨海默病→**阿茲海默症**、帕金森病→**帕金森氏症**、痲瘋→**漢生病**。最後一個尤其要緊——世界防治漢生病日的主旨就是消除污名，用污名化舊稱等於自打嘴巴。

## 五、浮動日期要寫成規則，不是寫死日期

51 個紀念日裡有 4 個是浮動的（1 月最後一個星期日、2 月第二個星期一、3 月第二個星期四、3 月第三個星期二）。寫死某一年的日期，隔年就全錯。

資料表存規則，由純函式解析：

```js
{ md: '02-04' }                        // 固定日
{ month: 3, weekday: 4, nth: 2 }       // 3 月第二個星期四（weekday 0=週日）
{ month: 1, weekday: 0, nth: 'last' }  // 1 月最後一個星期日
```

測試涵蓋 2026-2036 共 11 年，確保每筆在任意年份都解得出來，並包含閏年 2 月與「月底剛好是該星期幾」的邊界。`nth` 超出當月實際週數時**拋錯而非默默回傳下個月**——默默回傳會讓文章排到錯誤的日期，比整支失敗更難發現。

## 六、每年一篇同主題，怎麼不撞成關鍵字競食

同一個「世界癌症日」年復一年產新文，正是 [`duplicate-topic-gate.md`](./duplicate-topic-gate.md) 記載過的競食問題的溫床。

採用的結構（站長 2026-07-28 拍板）：

- 文章 slug 帶年份（`world-cancer-day-2027`），標題必須帶年份與當年度重點，靠「今年的官方主題與最新數據」天然區隔。
- 另建常青樞紐頁 `/topics/health-days/` 吃裸關鍵字並串起歷年。
- 寫作 prompt 帶入**往年同一紀念日的標題**，明確要求角度不得重複。
- 產線仍會過 `check-duplicate-topic.mjs`，標題相似度 ≥45% 就擋。

配圖同理：畫面主題寫死在年曆表（避免 51 篇 × 每年一輪漂移成全站同幾張聽診器），年度差異交給 `--context`／`--caption`；另用 `image-dedupe.mjs` 的 aHash 比對往年封面，撞了**只警告不剔除**——文章本身是好的，換張圖就好，而排程稿還有兩天可以人工處理。
