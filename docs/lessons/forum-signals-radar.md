# 論壇熱議當選題來源：純資料層先行，LLM 接在後面

**摘要**：想把 PTT/Dcard/Threads 的熱議接成常態選題來源，最後只有 PTT 可行；而且關鍵不在「接哪條線」，
而在**把抓取與過濾做成零 LLM 的純 script**，否則每小時跑一次會把整台機器的 Claude 額度吃光。

日期：2026-08-06　相關：[`auto-publish-pipeline-traps.md`](./auto-publish-pipeline-traps.md)、`docs/SERVER_HANDOFF.md` §cron 總表

---

## 問題

站長要從論壇熱門話題生選題（100% 避開政治），並希望每小時跑一次以追時效。
直覺作法是「開一條新的產線，每小時叫 Claude 讀 PTT 挑題」。這條路有三個坑：

1. **額度**：`claude-appi` 的 session 額度是**每 5 小時一個共用視窗**，而 24 小時的排程早已排滿
   （相鄰內容線最大間距只有 2h57）。每小時喚一次 Claude 會直接餓死既有內容線——警消那條出過這個事。
2. **來源可得性**：三個來源只有一個抓得到。
3. **政治過濾**：關鍵字黑名單擋不乾淨，但也不能全靠 LLM（那又回到坑 1）。

## 原因

### 為什麼不能每小時喚 LLM

排程密度不是設計偏好，是硬牆。原則寫的是「任兩條日更線相隔 ≥5h」，實務上已經守不住，
再塞一條每小時的 LLM 線等於每 1 小時就有一條線在搶同一個 5 小時視窗。

### 三個來源的實測結果（2026-08-06）

| 來源 | 伺服器端可抓性 | 實測 |
|---|---|---|
| PTT | ✅ | `search?q=recommend:N` 直抓，推文數可當熱度排序 |
| Dcard | ❌ | Cloudflare 403，`curl` 與 WebFetch 都被擋（含 `/service/api/v2/posts?popular=true`） |
| Threads | ❌ | 回 200 但是 JS 空殼，257KB 裡沒有任何貼文文字；公開熱門需登入，官方 API 無「熱門話題」端點 |

Dcard 的替代是用 WebSearch 加 `site:dcard.tw`，但拿不到熱度數值。Threads 連 Google 索引都稀疏，先不接。

### 為什麼關鍵字擋不乾淨

兩個實測案例：

- **地方板的市政攻防**：台南板前 12 篇有 6 篇是「南市府查台糖 / 高市府回應」這類，
  字面上沒有政黨也沒有政治人物名，任何關鍵字表都擋不到。
- **PTT 索引標題會被截斷**：`[新聞] 60天協議恐告吹！伊朗開出這驚人條件 川` ——
  「川普」被切成「川」，關鍵字比對必然漏。

**純 script 不可能做到 100%**，這是資料本身的限制，不是規則寫得不夠好。

## 解法

### 一、把「抓取 + 過濾 + 去重」做成零 LLM 的純資料層

`scripts/lib/forum-signals.mjs`：白名單看板 × 逐板推文門檻 → 政治關鍵字 → 噪音過濾 →
每板取頭部 → 跨次去重帳本。全部是純函式 + fetch，**沒有任何模型呼叫**。

`scripts/forum-radar.mjs` 的第一階段跑完，**沒有新熱題就 `exit 0`**。
一天大部分時段都會走到這裡，額度消耗＝0。這是每小時跑得起的唯一原因。
（同 `lifestyle-typhoon.sh` 的前置 gate 思路：先用便宜的方式判斷「要不要動用 Claude」。）

**去重帳本不可省**：PTT 熱門文會連續掛榜好幾小時，沒有帳本會每小時重推同一題。

### 二、政治排除做三層，接受第三層必須花 LLM

1. **看板白名單**（不是黑名單）——Gossiping／HatePolitics／Military／PublicServan 根本不進名單。
   黑名單永遠會漏，白名單才是可保證的那層。
2. **標題關鍵字**——擋政黨與政治人物。**刻意不擋行政機關**（金管會、衛福部、勞動部）：
   那是監理與便民題，屬財經／生活的正當題材，擋掉會把好題一起殺光。
3. **LLM 判斷**——地方板逐則（Haiku），加上選題 prompt 的全域 backstop。
   只有這層讀得懂上下文，能處理截斷標題與「表面行政、實質政治」。

第三層只在「有新題」時才跑，所以不違反第一點的額度設計。

### 三、噪音過濾要針對「逐日例行文」

首跑撈到 547 則，過半是寫不成文章的例行文：Stock 每天有盤中閒聊、三大法人、外資買賣超；
Baseball／NBA 每天有 LIVE、炸裂、今日某某、戰績、花邊。加上這類 pattern 與每板取頭部後降到 179 則。

### 四、抓取要帶重試

併發 4 抓 30 板時 PTT 會零星拒連（一次跑 4 板失敗、單獨重抓全部 200）。
併發降到 3 並加一次退避重試後 0 失敗。**單板失敗＝該分類整輪沒有候選**，
若剛好是 tech 那幾板連續失敗，科技就會長期沒題，所以不能放著不管。

### 五、單一來源、而且找不到第二個（2026-08-08 全面實測）

`ptt.cc` 對本機出口 IP 整台封鎖後改抓 `pttweb.cc`，等於這條線只剩一個來源。
為了補備援，在主機上把能想到的全掃過一遍，結論是**沒有能替代「PTT 推文數」的第二來源**：

| 候選 | 主機端實測 | 判定 |
|---|---|---|
| ptt.cc | IPv4 逾時；AAAA 是 IPv4-mapped（沒有真 v6）；telnet 23 也不通 | ❌ 整台 IP 被擋，不分協定 |
| pttweb.cc | 200、0.2–0.3s（`pttweb.cc` 與 `www.` 同一台，**不算獨立備援**） | 現行主來源 |
| webptt.com | 站活著，但看板列表區是空的（.aspx 只剩推薦文側欄），無推文數 | ❌ |
| moptt.tw | JS 空殼（`請啟用瀏覽器的 JavaScript`），找不到公開 API | ❌ |
| disp.cc | 連得到、標題完整含 `[標籤]`，有每板 Atom feed | ⚠️ 整板只 20 列、落後約一天；熱度欄是 disp 自己的瀏覽數（3~57）不是推文數；feed 夾帶全文 3.6MB |
| Dcard | 403 Cloudflare（與 2026-08-06 相同，沒解封） | ❌ |
| Mobile01／巴哈姆特 | 403 | ❌ |
| r.jina.ai／allorigins／corsproxy／codetabs | 422／408／403／521 | ❌ 代理也繞不過去 |
| Google Trends TW RSS | 200，10 則帶流量估計與時間 | ⚠️ 是搜尋熱度不是論壇，內容偏藝人人名 |

其他掛 PTT 名號的網域（ptt.tw、ptthito、pttcc.net…）已被賣成 ETF 工具或賭博站，不要照名字挑。

**關鍵是「推文數」而不是「標題」**：逐板推文門檻正是這條線每小時跑卻不燒額度、也不洗版的原因。
拿得到標題但拿不到熱度的來源（disp.cc）接上去，等於要嘛品質掉、要嘛把篩選丟給 LLM 去燒額度。
所以最後選擇**不補來源，改補失敗可見度**（見下）。

### 六、節流告警一定要帶「連續幾輪」

第一版守門只記 `lastAlertMs`、6 小時報一次，結果 2026-08-08 站長收到一則 ❌ 完全無法判斷
那是「剛壞掉一次」還是「已經連續壞第 8 輪」——得有人去翻 log 才知道，而告警的意義就是免去翻 log。

改成：**一波故障的第 1 輪一定報**，同一波之後每 6 小時再報一次，訊息固定帶
「連續第 N 輪、約 X 小時、起於某時」。另外兩個容易漏的細節：

- **抓得到候選要清帳本**，否則下一波故障會被上一波的 cooldown 蓋住而延遲出聲。
- **dry-run 只算不寫**。手動跑 dry-run 剛好撞上故障時，若寫進帳本會把 `lastAlertMs`
  蓋成現在，**吃掉下一輪 cron 的告警**——診斷動作反而讓故障變隱形。
- 訊息長度也要算：`.sh` 用 `tail -c N` 截，30 個板名就吃掉約 470 bytes，
  上限抓太緊會從**開頭**切掉「掃 N 板」與輪數資訊，也就是最該看的那幾行。

## 怎麼避免重犯

- **告警要能單獨回答「壞多久了」**。只記「上次報過的時間」的節流會讓剛壞掉與壞了一整夜
  長得一模一樣；一定要記連續計數與起始時間，並在訊息裡帶出來。
- 任何「節流／去重帳本」都要同時想清楚三件事：**何時累加、何時清掉、dry-run 要不要寫**。
  少想第三件，診斷用的手動執行就會污染正式判斷。
- 換來源前先接受一個可能：**可能根本沒有第二來源**。與其硬接一個訊號品質不對的備援，
  不如把「壞掉多久」講清楚，讓人能及時介入。
- 要在既有主機加「高頻」自動化，先問**「這一輪一定要喚模型嗎」**。能用純資料判斷的部分先做完，
  把模型留給真的需要判斷的那一小部分。判準：**跑一百次裡有幾次會真的需要模型？**
- 「接到哪條既有線」通常不是真正的設計問題，**資料源的形狀才是**。
  論壇是唯一天然跨分類的來源（一次請求拿到全部分類），把它劈成 7 份塞進 7 條線，
  等於在 7 個地方重建同一套抓取與過濾。
- 政治／敏感內容過濾**不要只做一層**，也不要幻想純字串比對能做到 100%。
  白名單負責「保證」，關鍵字負責「便宜」，LLM 負責「讀得懂上下文」，三者分工。
- 新增資料源前**先實測抓得到抓不到**（`curl` + WebFetch 各試一次），不要照著直覺假設。
