# 外部搜尋趨勢選題 SOP

> 這是「熱門／上升搜尋趨勢 → APPI 選題 → 文章曝光」的唯一操作正本。
> 程式只負責可重現的資料整理；文章是否值得寫、事實是否成立，仍由 Codex 依本 SOP 完成查證與內容 gate。

## 什麼情況要啟動

遇到下列任一情境，先跑趨勢雷達，再決定是更新既有頁或新增文章：

- 使用者提到熱門搜尋、上升搜尋、Google Trends、搜尋熱度、即時需求。
- 要做開學、節慶、天氣、健康警訊等有明顯時間窗的內容。
- `growth:backlog` 已經處理完當輪，但仍需要尋找下一批曝光機會。
- 每次固定成長巡檢的開頭；趨勢是選題訊號，不是取代 GSC 的成效資料。

## 唯一入口

在 repo 根目錄執行：

```bash
pnpm search:trends -- --limit 20
pnpm search:trends -- --json --save
```

第一條給人讀的候選清單；第二條把機器可讀快照存到 git 外的 state 目錄。來源、解析、分數與去重規則的正本是 `scripts/lib/search-trends.mjs` 與 `scripts/search-trends.mjs`，不要在文件或 prompt 另抄一套。

需要測試其他 RSS 時才使用：

```bash
pnpm search:trends -- --feed "https://example.com/trends.xml"
```

目前預設來源是 Google Trends 台灣 RSS。它提供搜尋詞、約略流量級距、時間與相關新聞，不提供可當成精確搜尋量的數字；報告只能使用「熱度級距」這個語意。

## 固定執行迴圈

### 1. 先取得現況

```bash
pnpm growth:backlog
pnpm growth:audit --gate1       # 伺服器有 GSC 金鑰時才跑
```

`growth:backlog` 用來找零內鏈、零點擊與缺主題頁；`growth:audit` 用來找已有曝光但沒有點擊的頁。趨勢候選要和這兩份清單交叉，而不是單獨追熱搜。

完成條件：本輪已知道「哪些既有頁可承接」以及「哪些題目可能需要新頁」；不能只貼一份熱搜列表就進入寫作。

### 2. 跑純資料雷達

雷達會依序完成：抓 RSS、解析、去重、時效過濾、熱度／適配度評分、既有文章撞題標記。這一步不喚 LLM、不改文章、不 commit、不部署。

判讀決策：

- `GO`：有至少一個 APPI 分類訊號、分數達門檻、沒有高風險標記，也沒有明顯既有同題頁。可進入本輪工作清單。
- `REVIEW`：有訊號但需要人工判斷，例如人物私生活、跨分類、資料不足或可能與既有頁競食。先查證，再決定更新或另開頁。
- `WATCH`：目前熱度、時效或站台適配不足。保留觀察，不為了湊篇數寫稿。
- `DROP`：純數字等不可形成讀者問題的雜訊，直接排除。

完成條件：每個進入工作清單的候選都有 `decision`、`score`、`categories`、`angle`、`newsItems` 與可能的 `overlap`；缺任何一項就回到雷達或標成 `REVIEW`。

### 3. 先決定「更新」還是「新增」

優先順序固定如下：

1. 熱搜和既有高曝光／零點擊頁是同一需求：更新既有頁的 title、description、開頭直答、FAQ 與內鏈。
2. 熱搜和既有頁相關但不是同一問題：在既有頁加入趨勢段落，必要時另開一篇解釋型文章，兩頁互鏈。
3. 站上沒有可承接的正本，且趨勢有足夠來源與讀者意圖：新增文章，建立語意化 slug、topic／column 與至少兩條有效內鏈。

不要因為候選分數高就複製新聞標題；熱搜只告訴我們「讀者正在找」，不告訴我們事實內容，也不自動授權侵犯私生活或未證實指控。

完成條件：每個候選已明確標記 `update` 或 `new`，並寫下一句「讀者要得到的答案」，不是只有關鍵字。

### 4. 查證再寫

文章動筆前完成下列查證：

- 至少一個第一手來源：政府、主管機關、官方公告、原始研究、賽事／機構官方資料或當事方公開說明。
- 重大新聞、人物、政策、跨國事件再補至少一個獨立來源；RSS 裡的相關新聞只能當線索，不能自動算交叉查證。
- 健康與醫療題：優先官方衛教、醫療院所或同儕審查資料；清楚寫警訊、限制與就醫界線，不把趨勢詞當診斷。
- 財經題：標示資料日期與風險，不把熱搜改寫成投資建議或報酬保證。
- 人物私生活、未定罪指控、災害與即時傷亡：沒有足夠可公開查證資料就 `SKIP`。

完成條件：文章中的每個關鍵數字、時間、人物關係與因果敘述都能回到可連線來源；查不到就刪掉或改成明確的不確定描述。

### 5. 寫作與成長 gate

新增或更新文章都要套用共用 `GROWTH_PROMPT`：

- title 前段放讀者真的會搜的詞，description 直接回答題目。
- 正文前三分之一至少有一條有資訊量的內鏈，全篇至少兩條，且 slug 必須已存在。
- 能對應既有主題才填 `topics`／`column`，不要自創不存在的 id。
- 適合時補 FAQ；醫療、政策、財經題補限制與資料日期。
- 內容使用繁體中文台灣用語，附來源與 disclosure，通過既有 content／tag／圖片 gate。

完成條件：`node scripts/growth-lint.mjs <file>` 沒有 `G1-none`；新文的來源、封面、內文圖與 frontmatter 也符合現有產線規則。

### 6. 導流、部署與索引

文章完成後，固定做三件事：

1. 從一篇既有高流量或高曝光頁連到新／更新頁。
2. 從新／更新頁連回開學專題、相關 topic hub 或同一需求的正本。
3. 跑 `pnpm build && pnpm check:links`；需要正式驗收時觸發 `gh workflow run deploy.yml --ref main`，再用正式網址檢查 title、description、dateModified、內鏈與 HTTP 200。

push、部署、IndexNow 是不同狀態；只有線上網址驗證成功才算「已上線」。

完成條件：沒有 broken internal link；正式頁能看到新 metadata 與至少一條預期的延伸閱讀，且部署 job 成功。

### 7. 回收訊號

趨勢文章不能用「發了」當成完成。回收時分開看：

- GSC：曝光、點擊、CTR、平均排名與實際 query；注意資料延遲，不把當日空窗當失敗。
- GA4：文章 landing page、使用者、下一頁瀏覽與回訪；確認導流是否真的增加 PV/session。
- 趨勢來源：下一輪是否仍有熱度、是否只是一次性事件；沒有延續就更新角度或停止追寫。

完成條件：每一篇都有後續動作 `keep`、`refresh` 或 `stop`；成效資料一律用 `weekly-data.mjs`、`growth:audit` 或 repo 的 `data/seo-daily/` 現算，不把一次讀數寫死在 SOP。

## 分數的固定語意

`search-trends.mjs` 的分數不是 Google 排名，也不是預測流量；它只是讓每次排序一致：

- 熱度：RSS 的約略流量級距。
- 時效：距離 RSS 發布時間越近越高，超過預設時效不進候選。
- 適配：標題是否對應 APPI 分類與既有讀者需求。
- 意圖：是否包含「怎麼、為何、是什麼、影響、注意」等可回答問題的訊號。
- 證據：RSS 是否附相關新聞，數量越多只代表線索較完整，不代表已查證。
- 扣分：既有文章撞題、純數字、人物私生活等風險。

改詞表或分數時，同步修改 `scripts/lib/search-trends.mjs` 的測試與本節語意；不要只改 Slack 文案。

## 自動化邊界與故障處理

- 雷達是純資料層，不能因為抓到熱搜就自動發布文章。
- 全部來源失敗要回報 `TRENDS_RESULT=FAIL`；不能把「抓不到」偽裝成「本輪沒有熱門題」。部分來源失敗時保留成功來源並明確列警告。
- 沒有合格候選是正常結果，回報 `TRENDS_RESULT=NONE`，不喚模型、不硬湊文章。
- 快照放 git 外 state 目錄，避免 cron 污染工作區；Slack 只走 `scripts/cron-report.mjs`，不在新腳本裡直打 API。
- 真正寫稿、改站、部署仍遵守 `CLAUDE.md`、`docs/automation-invariants.md`、`docs/growth-playbook.md`；本 SOP 不能繞過它們。

## Codex 每輪交付格式

完成一輪後，用以下順序回報，讓下一輪可以直接接手：

```text
趨勢來源／抓取時間：
GO 候選：<題目> → update/new → <來源數> → <預計文章角度>
REVIEW 候選：<題目> → 卡在哪個查證或撞題風險
本輪已完成：<檔案／正式網址／部署 run>
下一輪：<keep／refresh／stop 或下一批候選>
```
